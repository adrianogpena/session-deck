# Session Deck

A VS Code extension that gives you an **agent-deck-style overview of AI coding sessions across all your projects**, in a sidebar, using a single reusable tab to view them.

Renamed from "Claude Deck" because Claude Code was only the *first* backend: it now also surfaces GitHub Copilot CLI sessions, discovered and resumed side by side with Claude ones in the same sidebar (possibly more agents later). See the Architecture section for how the two backends are isolated (`discovery/claudeStorage.ts` vs. `discovery/copilotStorage.ts`) behind a small `AgentType` dispatch, rather than the tree/terminal logic being a rewrite per agent.

Built as a learning project, based on:
- **[Claude Sessions Explorer](https://github.com/ShahadIshraq/claude-session-vs-code-extension)** — reading Claude Code's local session storage and driving the real CLI.
- **[agent-deck](https://github.com/asheshgoplani/agent-deck)** — the "mission control" list-of-sessions UX (can't be used directly on native Windows, it needs tmux via WSL).

See `../ACTION_PLAN.md` for the broader terminal-tooling research this grew out of.

## What it does right now (skeleton)

- Reads `~/.claude/projects/<encoded-path>/*.jsonl` — this is where Claude Code stores every session, for every project, machine-wide. The sidebar only shows the subset your current workspace has explicitly opted into (see the per-workspace project list below) — it's a curation tool, not a firehose of everything you've ever used Claude Code on.
- Each session's label is its first *real* prompt (truncated), with a relative "last touched" timestamp. "Real" excludes synthetic "user" turns that aren't something you typed — slash-command echoes (`<command-name>`, `<local-command-stdout>`, etc.), usage-limit notices, subagent/sidechain markers (`agentId:`) — so a session that started with `/init` doesn't get titled "`<command-name>/init</command-name>`" (`discovery/claudeStorage.ts:isDisplayableUserPrompt`, ported from the reference extension's `content.ts`). It also handles a prompt's `content` being an array of blocks (tool results, images, …) as well as a plain string, joining any `text`/`thinking` blocks — previously only plain-string turns were recognized at all.
- **A project only ever shows its 5 most recently modified *active* sessions** (`MAX_SESSIONS_PER_PROJECT_VIEW` in `tree/sessionProvider.ts`) — a project easily accumulates dozens of sessions over time, and showing all of them made the tree unreadable. The 5 shown are picked by cheap `fs.statSync` mtime comparison *before* any transcript is parsed for its title, so capping doesn't cost anything extra; a project's tooltip notes "Showing the 5 most recent of N sessions" when it's actually truncating. **Search Sessions** and the **Open Sessions** view both go through the uncapped `listAllSessions()` instead (archived sessions included), so nothing is ever unfindable.
- **Sessions beyond the cap are archived, not just hidden** (`sessionProvider.ts:enforceArchiveCap`) — when a genuinely *new* session pushes a project's active count past 5, the oldest active one is automatically archived to make room, moving it under that project's collapsed "Archived (N)" node instead of just falling off display. If it currently has an open terminal, that terminal is closed too (`AgentTerminalService.closeSessionTerminal`) — an archived session was never meant to keep running in a tab that's no longer visible anywhere. This only triggers on a *newly discovered* session, tracked in-memory per project (`knownSessionIdsByProject`): the very first time a project is listed in a given VS Code session is always a baseline, never an eviction — otherwise every project with a long pre-existing history would get mass-archived the moment this shipped, which manual archiving stays exempt from a second way too: a session you archive by hand (✏️-row "Archive" icon, or right-click) never gets silently re-archived just because it's still old the next time the cap is checked. Resuming an archived session (clicking it, or via Search) automatically unarchives it first (`ensureSessionActive` in `extension.ts`) — there's no such thing as an actively-open archived session. The eviction decision itself is pure and unit-tested (`tree/archivePolicy.ts`, `test/suite/archivePolicy.test.ts`), separate from the vscode-API-heavy bookkeeping around it.
- **Session reads are cached by file mtime** (`discovery/claudeStorage.ts:readSessionMeta`) — a session's cwd + title are parsed from its transcript in one pass the first time it's seen, then served from cache on every later refresh until the file's mtime actually changes. Before this, every tree refresh re-parsed every session's transcript from scratch. Manual refresh (`sessionDeck.refresh`) clears this (and the git-root and search-text caches below) so nothing is ever served stale on demand.
- **Clicking a session resumes it in a real terminal, one terminal per session** — `claude --resume '<sessionId>'`, ported from the reference extension's `terminal.ts` (`src/terminal/terminalService.ts`): checks `claude` is actually reachable on PATH first (falling back through the user's login shell, since the extension host's PATH is often narrower than an interactive shell's), and sends the command via shell integration (with a "Waiting for terminal to be ready…" progress toast) rather than raw `sendText`, so a slow-starting shell can't eat the first few characters of the command. Every terminal it creates is given the right agent's mark as its `iconPath` (`agentIconPath(extensionUri, session.agent)` in `tree/agentIcons.ts`), so its tab reads as the right agent's session at a glance in the Terminal panel — without that, VS Code falls back to whatever icon the underlying shell profile has (Git Bash's, on this machine), which looks unrelated. Copilot's mark is a near-black `#141413` glyph, invisible against a dark theme, so `agentIconPath` gives it VS Code's `{ light, dark }` icon form specifically — `resources/copilot-mark.svg` in a light theme, a white-filled `resources/copilot-mark-dark.svg` in a dark one; Claude's brand orange reads fine on either, so it stays a single flat icon. Re-clicking the session that's already active just `.show()`s its terminal — switching to a *different* session never touches whatever's running in another session's terminal: no interrupt, no visible "logout/login" flicker, and no orphaned live status (a session left running in the background keeps firing its own hooks normally). Every terminal is also created with `isTransient: true`, which opts it out of VS Code's own persistent-terminal-session restore — without it, closing and reopening the window (with `terminal.integrated.enablePersistentSessions` on, the default) would bring the tab back as a blank, session-less terminal, since nothing survives a fresh extension activation to reconnect it to. `AgentTerminalService.dispose()` (wired via `context.subscriptions`) additionally closes every tracked terminal outright on a *graceful* shutdown (reload/disable) — belt-and-suspenders, not the actual fix, since `dispose()` isn't reliably called on an abrupt window close, only `isTransient` is guaranteed to apply regardless. An earlier version of this tried a single shared terminal, interrupting the running session with Ctrl+C to reuse the tab for a different one, to match the single-tab philosophy used for the transcript view below — but that philosophy only holds for *passive* views; there's no way to "pause" a foreground CLI process without either killing it or moving it out of the way, confirmed by checking how even the desktop Electron "Claude Terminal" app (`Sterll/claude-terminal`) does it: a `Map<id, ptyProcess>` of concurrently-alive processes, never one shared pty.
  - **View Transcript** (👁, hover or right-click a session) — a secondary action for skimming without spinning up a CLI session: opens a read-only markdown transcript, **always in the same tab**. Not a webview trick — VS Code's own "preview tab" behavior. Every session is a distinct virtual document (`session-deck:/<project>/<sessionId>.md`) opened with `{ preview: true }`; VS Code's editor already replaces one preview tab with the next unless you pin it, so switching sessions just swaps the content of one tab. (This one genuinely is a passive view, so the single-tab approach is the right fit here — unlike the live terminal above.)
  - **Open Session in New Terminal** (empty-window icon, hover or right-click a session) — always opens a brand-new terminal for that session even if one's already tracked, e.g. to run it twice side by side or recover from a terminal stuck in a bad state.
  - **Resume Session in Terminal (Skip Permissions)** (right-click only, no inline icon) — `--dangerously-skip-permissions`, gated behind an explicit confirmation dialog by default — turn it off via the `sessionDeck.confirmDangerousSkipPermissions` setting (read live, no reload needed; ported from the reference extension's own setting of the same name/default) if you find it more annoying than useful. Always goes through "open in new terminal", deliberately bypassing the reuse check: silently reusing an already-open non-dangerous terminal for the same session would ignore the flag the user just confirmed.
  - **Copy Last Response** / **Copy Session Info** (right-click only, no inline icon — the row already has four) — the first copies just the last assistant reply's text (`discovery/claudeStorage.ts:readLastAssistantResponse`, a fresh full scan of the transcript each time) to the clipboard, for pasting a fix or an answer somewhere else without opening a terminal or the transcript view. The second copies a plain-text block (display name, project, cwd, session id, last-modified, live status if tracked, transcript path) — for pasting into an issue, a chat with a teammate, or another Claude session.
- A refresh button in the view title bar, plus a best-effort live file-watcher on `~/.claude/projects`.
- **Projects are grouped by git repo root, not by raw `~/.claude/projects` folder.** Each session's `.jsonl` records the *exact, unencoded* cwd Claude Code was launched from (`discovery/claudeStorage.ts:readSessionMeta`) — no more guessing from the lossy encoded folder name. That cwd is resolved to a project root via `git -C <cwd> rev-parse --git-common-dir` (`discovery/gitProject.ts`), which naturally folds a repo's subfolders (`.idea/localDebug`) *and* linked worktrees (`.claude/worktrees/<branch>`, created by the EnterWorktree tool) into the **same** project, since they all share one `.git` common dir. A folder that isn't a git repo just becomes its own project, keyed by its raw cwd. Default project name is `path.basename(root)` — so `X:\Source\miles-core` and `X:\Source\miles-core\.idea\localDebug` both become one **`miles-core`** project, not two, and not `core`.
- Sessions whose cwd isn't exactly the project root (e.g. that `.idea/localDebug` one) show the relative subpath next to their timestamp, so you don't lose that context once they're merged into one project.
- Hover a project for a new-session ("+"), rename (✏️), and remove (🗑) icon, or right-click for the same actions in the context menu.
- **"+" on a project starts a brand-new Claude Code session there** (`sessionDeck.newSession` → `AgentTerminalService.startNewSession`) — plain `claude` (no `--resume`), always in a fresh terminal, rooted at the project's own resolved root path (not any particular linked worktree/subfolder member, even if the project has several). A "New Session (Skip Permissions)" variant is available from the context menu, gated behind the same confirmation dialog as the equivalent resume action. **Claude-only for now** — on a Copilot project node (only reachable once the tree is showing the `claude`/`copilot` split), both actions just show an explanatory message instead of silently starting a Claude session under a Copilot project by mistake.
  - **The new session's terminal is linked back to it automatically, so re-selecting it later reuses that terminal instead of opening a second one.** There's no CLI flag to pre-assign a session id (checked: no `--session-id`; `--name` is a separate alias layered on the auto-generated id, not a substitute for it, so it doesn't help either — and neither reference extension actually solves this: `ShahadIshraq`'s has no "new session" feature at all, and `Sterll/claude-terminal`'s Electron app never needs to, since it renders raw `node-pty` output directly under its own ids rather than correlating with Claude Code's on-disk session storage). `correlateNewSession` polls `~/.claude/projects` every 500ms (up to a generous 60s) for the next brand-new `.jsonl` file to appear, and registers that file's real session id against the terminal that started it. This used to watch for `fs.watch`'s `rename` event instead — fires exactly once, specifically on creation — but on a real, large, actively-churning `~/.claude/projects` tree (one already carrying a second independent recursive watcher from `SessionTreeProvider.watch()`), that recursive watch reliably dropped the new file's event outright, confirmed via logging that showed a full timeout with no event ever seen for the new file, twice in a row, even though the file did exist by the time of a manual refresh — a known reliability limitation of Windows' `ReadDirectoryChangesW`-backed recursive watching under a busy tree. Polling sidesteps OS notification delivery entirely by just re-reading the directory structure directly. The 60s window (up from an original 15s) turned out to matter for another reason: with shell integration never activating in this environment, `claude` only gets typed in via a blind `sendText` fallback 500ms after the terminal is created, and a slow-starting shell profile pushed the real session-file creation past 10s in testing. Deliberately does **not** wait for that file to record a matching `cwd` first: a session's `cwd` is only written on its first actual *user* turn (confirmed against real transcript data), not on the startup metadata records Claude Code writes immediately — so clicking the tree entry before typing anything into the fresh terminal would leave a cwd-matching approach still waiting, which was the actual bug an earlier version of this had. `claimedByCorrelation` guards against two "New Session" clicks in quick succession both grabbing the same newly-created file. Once correlated, the tab's "New: " prefix is dropped too, but only if it's still the visibly active terminal — there's no direct rename API, only a command that also switches the active terminal tab as a side effect, which would be a worse surprise than a stale label if the user has since moved on.
- **`.vscode/session-deck.json` is the sole source of truth for what the sidebar shows.** No file, or `{ "projects": [] }`, means an empty sidebar — Session Deck never falls back to "show everything discovered", by design: this is meant to be a curated, per-workspace view, not a dump of every project you've ever pointed Claude Code at. Shape: `{ "projects": [{ "root": "<git root>", "name": "<display name>" }, ...] }`, keyed by the same resolved git root as everything else (a bare string entry also still works, treated as `{ "root": "<string>" }` with no name override). An entry's `name` is this file's whole point: it's meant to be hand-edited directly, and always wins over the default (last path segment) name — there's no other place a project's display name can come from. Chose `.vscode/` over `.claude/` for this file: `.claude/` is Claude Code CLI's own config directory with its own schema, and this is purely a VS Code extension's workspace setting.
  - **"+" button in the view title** (`sessionDeck.addProject`) opens a picker listing every project Session Deck has discovered under `~/.claude/projects` that isn't already on this workspace's list, plus a top "Add a project folder not listed here…" entry that opens a folder-picker and resolves its git root (works even for a folder with zero Claude Code sessions yet). Creates the file if it doesn't exist yet. Always writes an explicit `name` (the default display name at the time it's added) rather than a bare `{ "root": "..." }` — every entry is self-documenting and immediately editable, and removing then re-adding a project doesn't quietly drop its `name` field (it *does* still reset to the default name, though — there's nowhere else a previous custom name could be remembered once its entry is deleted).
  - **Edit button (✏️) in the view title**, next to "+" (`sessionDeck.editProjectList`) opens `.vscode/session-deck.json` directly in the editor for hand-editing (both membership and names). If this workspace doesn't have one yet, it's created first as an empty `{ "projects": [] }` — populating it is what "Add Project" and hand-editing are for, not this button.
  - **Remove** (🗑, hover or right-click a project) just takes the entry off `.vscode/session-deck.json` — a project can only ever be in the tree because it's on that list, so there's nothing else for "remove" to mean anymore.
  - **Hide** (right-click only, no inline icon — `sessionDeck.hideProject`) sets `hidden: true` on the entry instead of removing it: the project (and whatever `name`/other overrides it carries) drops out of the tree but stays in the file, unlike Remove. No confirmation dialog (it's non-destructive), but there's also deliberately no "Unhide" button anywhere — a hidden project isn't shown anywhere to attach one to — so the info message after hiding points at hand-editing the file (`sessionDeck.editProjectList`) to bring it back, either flipping `"hidden"` to `false` or removing the key.
  - **Four more per-project overrides**, all optional, all hand-edited via the same file (`config/workspaceConfig.ts`'s `WorkspaceProjectEntry`): `dangerouslySkipPermissions: true` skips the "Skip Permissions" confirmation dialog for that project specifically, regardless of the global `sessionDeck.confirmDangerousSkipPermissions` setting — a one-way "I trust this project" exception, no way to force confirmation back on for one project while it's off globally; `maxSessionsShown: <number>` overrides the default 5-session active cap (and the auto-archive threshold that goes with it) per project; `emoji: "🚀"` prefixes that literal emoji onto the project's tree label; `color: "green"` (one of `COLOR_SWATCH_EMOJI`'s named swatches in `tree/sessionProvider.ts` — the usual color names) prefixes a colored-circle emoji instead, if `emoji` isn't also set. `color` is plain text prefixed onto the label rather than a `ThemeColor`'d icon deliberately — the latter washes out to the row's plain foreground when the row is selected, the same reason session status uses a `FileDecoration` instead of its icon.
  - The file is watched, so hand-editing it (or a teammate committing one) refreshes the tree automatically.
- **Rename a project or a session** (✏️, hover or right-click) — for a project, this writes its `name` field in `.vscode/session-deck.json` directly (the same field you can hand-edit); for a session, it's stored as an override in extension `globalState` (`src/config/state.ts`) keyed by session id (a UUID, so it's already globally unique) — sessions aren't part of the workspace file, since they're not something you curate a membership list of the way projects are.
- **Search Sessions** (🔍, view title) — full-text search across every configured project's session content (every displayable user prompt + assistant reply, not just the first prompt), via a `QuickPick` with live filtering as you type. The per-session text is built lazily on first use (and cached by mtime, same as above), so only the very first search pays the cost of reading every transcript; picking a result resumes that session in a terminal, same as clicking it in the tree. A leading status prefix filters by status instead of/alongside text — `!` running, `@` waiting, `#` done, `~` error (`extension.ts`'s `SEARCH_STATUS_PREFIXES`, the same three of agent-deck's four plus the new error state; typing just the prefix alone lists every session in that status).
- **Case-insensitive path matching on Windows** (`discovery/pathUtils.ts:normalizeFsPath`) — a git-resolved root and a hand-typed `.vscode/session-deck.json` entry that differ only by drive-letter/segment casing (e.g. `X:/Source/miles-core` vs. `x:\source\miles-core`) are still treated as the same project everywhere they're compared: grouping discovered sessions, matching a workspace-list entry back to its sessions, and add/remove/rename. Previously these were plain string equality checks, so a casing mismatch would have silently shown a project as empty.
- **Live session status dots** — 🔴 running, 🟡 waiting for input, 🟢 done, 🔴✗ error, or nothing (untracked, or a "done"/"error" you've already seen — see below). This section covers **Claude's** mechanism, which needs an explicit opt-in below; **Copilot's** is always-on and needs none — see the Copilot bullet earlier in this list. Opt-in via **"Session Deck: Enable Live Status Tracking"** (Command Palette) — it shows the exact change before writing anything, since it edits Claude Code's own *global* `~/.claude/settings.json`, not a per-workspace file:
  - Adds 4 [hook](https://code.claude.com/docs/en/hooks) entries — `UserPromptSubmit` → running, `Stop` → done, `Notification` → waiting, `SessionEnd` → clears the status file entirely (back to "no status", since the process is actually gone — not a fourth persistent green-forever state) — each running the bundled `src/status/reportStatus.ts` (compiled to `out/status/reportStatus.js`) as a plain `node` command. `Stop` fires on every ordinary turn completion (the everyday "task finished" moment); `Notification` is filtered, via the hook's `matcher`, to only `permission_prompt`/`agent_needs_input`/an MCP elicitation dialog — things that genuinely need *your* action — explicitly excluding `notification_type: idle_prompt`, Claude Code's automatic "you've been idle a while" nudge that otherwise fires on its own timer regardless of anything you do. `status/reportStatus.ts` re-checks `notification_type` itself too, in case a given Claude Code version doesn't honor the matcher. Merging is additive, idempotent, and self-healing (`src/status/claudeSettings.ts`): an entry is recognized as "ours" by matching `reportStatus.js` in the command string, not the full exact path — so "Enable" replaces *any* older-shaped version of its own hook entries, including one whose path is stale (an extension reinstall/move, or a source reorganization — this broke once already: a folder restructure changed the compiled path from `out/reportStatus.js` to `out/status/reportStatus.js`, and the old exact-string matching left the stale entries in place, quietly erroring on every hook invocation until "Enable" was run again) instead of running both old and new side by side, or leaving a broken one behind forever. Existing *other* hooks/settings are always left untouched. "Session Deck: Disable Live Status Tracking" removes every entry it added, in any shape, regardless of whether it's the current exact command.
  - **Why the filter matters**: `Notification` hooks fire asynchronously — "Claude Code continues without waiting for the hook to finish" — so an unfiltered `idle_prompt` could have its (slow) write land *after* a fast `UserPromptSubmit` write and incorrectly flip a freshly-"running" session back to "waiting", and would also flip a "done" session to "waiting" on its own after a while with no user action at all. Filtering it out at the source (so Claude Code never even invokes the script for it) fixes both.
  - `status/reportStatus.ts` is a deliberately standalone script — no `vscode` import, no dependency on the rest of the extension — since it runs as a separate `node` process spawned by the real `claude` CLI, outside the extension host entirely, reading the hook's JSON payload (`session_id`, `hook_event_name`, `notification_type`, ...) from stdin per Claude Code's hook protocol. It writes one small JSON file per session to `~/.claude/session-deck-status/<sessionId>.json`; it never blocks or alters a prompt/tool call (always exits 0).
  - **"Done" and "error" are informational, not a pending request — once you've seen either, it clears to blank.** Unlike "waiting" (a real ask that only clears when you actually resolve it, via a fresh hook event), a green "done" or red "error" dot just means "something happened, you haven't looked yet." Selecting that session in the tree (`status/sessionStatus.ts:acknowledgeSessionStatus`, wired to `TreeView.onDidChangeSelection`) marks that specific event as seen, in memory only; it goes back to no status until a newer event (a fresh `running`, etc.) supersedes it.
  - **"Error" isn't a hook event — it's inferred from the resumed `claude` command's own exit code**, via shell integration's per-command completion event (`terminalService.ts`'s `onDidEndTerminalShellExecution` listener, keyed off the specific `TerminalShellExecution` `launch()` started). Claude Code's hooks don't distinguish a fatal error from a normal turn end (confirmed: `Stop` fires the same way either way), so this is the only signal available — and only a best-effort one: it only covers a session *resumed* through Session Deck (not a brand-new one, since there's no session id to attach the exit code to until correlation finishes), and only a real, positive exit code counts. `exitCode` comes back `undefined` for a Ctrl+C cancel, a sub-shell being opened, or a misbehaving shell integration script (per `TerminalShellExecutionEndEvent.exitCode`'s own documentation) — all correctly left alone rather than misread as a crash. Written via `status/sessionStatus.ts:markSessionError`, the one status this extension writes directly rather than via `reportStatus.ts`.
  - **Closing a session's terminal clears its status too, even mid-task.** VS Code kills the terminal's process tree outright when its tab closes (there's no graceful detach on native Windows the way tmux/screen would allow) — so Claude Code may never get the chance to fire its own `SessionEnd` hook, and without this, a session closed while "running"/"waiting" would show that color forever. `AgentTerminalService`'s `onDidCloseTerminal` listener (the same one that already untracks the terminal for reuse purposes) also calls `status/sessionStatus.ts:clearSessionStatus` directly — idempotent, so it's a harmless no-op if the session had already exited cleanly and the hook got there first.
  - **Status color survives selection, on a separate rendering layer.** A `TreeItem.iconPath` colored via `ThemeColor` gets washed out to the row's plain foreground when that row is selected — a VS Code tree-rendering quirk. `status/sessionStatusDecorationProvider.ts` colors the dot via `vscode.FileDecoration` instead (the same mechanism Git/SCM status colors use, via `resourceUri` on the tree item), which reliably keeps its color regardless of selection state.
  - `status/sessionStatus.ts` reads the raw status files (`readSessionStatus`) and layers the "seen" logic on top (`readEffectiveSessionStatus`, what's actually displayed). A filesystem watcher on the status directory (`SessionTreeProvider.watch`) repaints both the tree and the decorations live as hooks fire, the same pattern already used for `~/.claude/projects`.
  - **A real OS desktop notification fires the moment an open session's status transitions *into* "waiting" or "error"** (`status/waitingNotifier.ts`'s `WaitingNotifier`, via the [`node-notifier`](https://www.npmjs.com/package/node-notifier) package — the extension's first actual runtime dependency; `vscode.window.showInformationMessage` is an in-app toast only, easy to miss while working in a different application entirely). Only *transitions* notify, never a repeat while a session stays in that state, and never a session's first sight (so opening the extension onto an already-waiting session doesn't immediately notify) — the same "first sight is a baseline, not an event" reasoning as `sessionProvider.ts`'s auto-archive cap. Only currently-open sessions (`AgentTerminalService.getOpenSessions()`) are watched, checked on the same status-directory-changed tick as everything else. There's no stable VS Code API to force the OS window itself to the foreground — clicking the notification balloon is what actually does that, an OS behavior outside this extension's control; `onActivated` (best-effort, unverified interactively: depends on the platform notifier reporting a genuine click rather than a dismiss/timeout) is the closest available from inside the extension, and just brings that session's already-open terminal to the front within the window (`AgentTerminalService.revealSession`).
  - Researched from **[anthropics/claude-code](https://github.com/anthropics/claude-code)** — not the CLI's source (that's closed-source, confirmed: the installed `anthropic.claude-code` VS Code extension ships a single ~3.6MB minified `extension.js` with no `license`/`repository` field), but this repo's `mods/types/claude-code.d.ts` documents the full hook event list and payload shapes, `examples/hooks/` confirms the stdin-JSON / exit-code protocol, and the [official hooks docs](https://code.claude.com/docs/en/hooks) document the exact `notification_type` values and the "hooks run in parallel/async, no ordering guarantee" behavior that motivated the matcher filter.
- **GitHub Copilot CLI sessions are discovered and resumed the same way, side by side with Claude's.** Copilot CLI keeps a single shared SQLite database for every session on the machine, `~/.copilot/session-store.db` (`sessions(id, cwd, repository, ...)` + `turns(session_id, user_message, assistant_response, ...)`), read via Node's built-in `node:sqlite` (`DatabaseSync`, `readOnly: true`) in `discovery/copilotStorage.ts` — no new dependency. It must be opened at its real path, not a copied snapshot: the database runs in WAL mode, so a plain file copy misses whatever's still sitting in the `-wal` file and under-reports sessions (confirmed against real data before settling on in-place reads). Each Copilot session records its own `cwd`, so it's grouped into a project via the exact same `resolveProjectRoot` git-root resolution Claude sessions use (`copilotSessionsForRoot` in `sessionProvider.ts`) — **if a session's `cwd` and `repository` fields ever disagree about which project it belongs to, `cwd` wins**, since that's what every other part of this extension already keys off of. `.vscode/session-deck.json` needed no new field for this: a project entry is just a root + name as before, and whichever agent(s) actually have sessions under that root are what determines what shows — nothing declares "this project is Claude" or "this project is Copilot" anywhere.
  - **The tree shows a `claude` / `copilot` grouping folder above the project level, but only when sessions actually exist for both agents somewhere on the machine** (`SessionTreeProvider.getRootNodes`/`detectAgentsInUse`) — if only one agent has any sessions at all (the common case today, e.g. Copilot never used yet), the tree collapses back to today's flat `Project → Session` shape with no wrapper folder, exactly as before this feature shipped.
  - Resuming a Copilot session works exactly like Claude's: `copilot --resume=<sessionId>` (`terminal/copilotCommand.ts:buildCopilotResumeCommand`) sent to a terminal the same way, with `--allow-all` standing in for Copilot's skip-permissions equivalent when "Skip Permissions" is used. **Starting a brand-new Copilot session from the tree isn't supported yet** — the "+"/"New Session" actions on a Copilot project node show an explanatory message instead of silently launching the wrong agent; only resuming an existing Copilot session works today.
  - View Transcript, Copy Last Response, and Copy Session Info all work for Copilot sessions too, rendering from `turns` (`## You` / `## Copilot` headings) instead of a `.jsonl` file. Search Sessions searches both agents' content together.
  - **Live status tracking works for Copilot sessions too — running/waiting/done/error dots and desktop notifications, same as Claude's — but through a different mechanism, and always-on with no opt-in.** `status/copilotStatusWatcher.ts` tails `~/.copilot/session-state/<sessionId>/events.jsonl`, an activity log Copilot CLI already appends to unconditionally (for its own IDE/resume support), rather than Copilot's own opt-in `hooks` config (`.github/hooks/*.json`) — no settings mutation, no "Enable Live Status Tracking" step, no spawned process per event; only the *new* bytes appended after a Copilot session's terminal opens are tailed (never its history), the same "baseline on first sight" reasoning as the auto-archive cap. Its `assistant.turn_start`/`assistant.turn_end` map to running/done, `permission.requested`/`elicitation.requested`/`user_input.requested` to waiting, their `.completed` counterparts back to running (a resumed-after-approval signal Claude's own hook set can't express at all), `session.error` to error, and `session.shutdown` clears the status — written through the exact same `status/sessionStatus.ts` file Claude's hook script writes, so the decoration provider, `WaitingNotifier`, and the tree's tooltip all work unchanged, with no agent-specific branching anywhere downstream. This reads Copilot CLI's own internal, undocumented on-disk format rather than its versioned public API, confirmed by extracting the event vocabulary directly from the CLI's bundled `session-events.schema.json`; if a future Copilot CLI release changes that shape, this degrades silently (status just stops updating) rather than breaking anything.
- **"Open Sessions" view in the built-in Explorer sidebar** (`src/tree/activeSessionProvider.ts`) — the reference extension does the same thing (`contributes.views.explorer`, confirmed in its `package.json`), surfacing its full session browser there too. Session Deck deliberately does *not* mirror the full project/session tree into Explorer — that's a lot of information to add on top of a file tree you're already looking at. Instead this view shows exactly the sessions that currently have an open terminal **in this window** (`AgentTerminalService.openSessionIds()`) — not "every running/waiting session on the machine", which could include one from a different window entirely. Each row's status label reflects `readEffectiveSessionStatus` when live tracking is enabled (running/waiting for input/done), or just "open" when it isn't — a session stays listed for as long as its terminal is, regardless of status, including after it's finished ("done"). Typically 0 or 1 rows, occasionally a few if several sessions are open at once. Starts collapsed (`"visibility": "collapsed"`) so it doesn't push the file tree down by default. Clicking an entry resumes it the normal way (the shared per-session terminal). The view refreshes on `AgentTerminalService.onDidChangeOpenSessions` (fired whenever a terminal is tracked/untracked) as well as on status-file changes, so it stays live without needing status tracking enabled at all — that's only needed for the status label to be more specific than "open".

## What it deliberately does NOT do yet

This is a skeleton, not the finished tool. Known gaps, in rough priority order:

1. **Claude's status tracking still needs manual opt-in and doesn't fully replicate agent-deck's states.** Its "error" status is inferred heuristically from the resumed `claude` command's own exit code, not a hook — Claude Code's hooks don't expose a distinct failure signal the way Copilot's `session.error` event does (see above). `quota_auto_resume_*` notification types (rate-limit handling) also aren't reflected in any status yet.
2. **No fork** (agent-deck's `f`/`F`) — archive/unarchive (`A`/`Shift+U` in agent-deck) is now implemented; forking a session (branching a new one from an existing session's context) isn't, and needs checking whether the `claude` CLI even supports it before it's worth pursuing.
3. **`decodeProjectPath` is now only a last-resort fallback** — used only when a `~/.claude/projects` folder has zero sessions with a recorded `cwd` (old/corrupt data). It's still lossy for that rare case; everything else uses the real recorded cwd instead.
4. **Git root resolution spawns `git` per unique cwd** (cached in-memory per session, cleared on manual refresh). Fine for a personal project count; would need batching/throttling if this ever needs to scale to hundreds of projects.
5. **Claude and Copilot CLI today; agent-deck covers more (Codex, Gemini, OpenCode)** than this does yet. Adding another backend follows the same shape Copilot did: a parallel `discovery/<agent>Storage.ts` plus a small dispatch in `tree/sessionProvider.ts`'s discovery step and `terminal/terminalService.ts`'s command-building step — not a rewrite.
6. **No brand-new Copilot sessions from the tree yet** — only resuming an existing one, deliberately scoped out of this pass. `startNewSession`'s correlation approach for Claude (poll for the new session file to appear) would likely need to poll `~/.copilot/session-store.db` instead of a filesystem watch, but that hasn't been built or tested.
7. **`.vscode/session-deck.json` only supports single-root workspaces** — it always reads/writes `workspace.workspaceFolders[0]`. A multi-root workspace's other folders are ignored for this file.
8. **Search reads every configured session's full content into memory** the first time it's used per activation (batched sequentially, no `BATCH_CONCURRENCY`-style chunking like the reference extension uses) — fine at personal scale, would want batching if session counts grow much larger.
9. **The hook command's path is a hard-coded absolute path** into wherever this extension is currently installed/checked out (`context.extensionPath` at the moment "Enable" was run) — moving or reinstalling the extension elsewhere breaks the hook silently until re-enabled.

## Architecture

- `src/discovery/claudeStorage.ts` — no `vscode` dependency; raw reads of `~/.claude/projects` (list project folders, list a folder's session files). Also where a message's display text is extracted (`extractText`/`extractAssistantDisplayText`, handling both plain-string and array-of-blocks `content`) and filtered (`isDisplayableUserPrompt`, screening out slash-command echoes and other synthetic "user" turns) — both ported from the reference extension's `discovery/content.ts`. `readSessionMeta` (cwd + title, one pass, mtime-cached) and `readSessionSearchText` (full content for search, mtime-cached separately since it's only needed on demand) are the two cached readers everything else is built on, mirroring that extension's `discovery/service.ts` cache-by-mtime approach. `readLastAssistantResponse` (for "Copy Last Response") is a third, uncached full scan — a one-off user action, not something read on every refresh.
- `src/discovery/copilotStorage.ts` — no `vscode` dependency; Copilot's analogue of `claudeStorage.ts`, reading `~/.copilot/session-store.db` directly via `node:sqlite`'s `DatabaseSync` (`readOnly: true`) instead of parsing `.jsonl` files. `withDb()` opens a fresh connection per call rather than holding one open, mirroring `claudeStorage.ts`'s no-persistent-handle style. `listCopilotSessions()`/`listCopilotTurns(sessionId)`/`lastCopilotAssistantResponse(sessionId)`/`copilotSessionSearchText(sessionId)` are the Copilot-side counterparts to `claudeStorage.ts`'s equivalents. Must read the real file path in place, never a copy — the database runs in WAL mode, so a copied snapshot silently misses rows still sitting in the `-wal` file. `src/types/node-sqlite.d.ts` is a small hand-written ambient module declaration filling a gap in the installed `@types/node@^20.11.0`, which predates `node:sqlite`'s addition to Node's typings.
- `src/discovery/pathUtils.ts` — no `vscode` dependency; `normalizeFsPath` for case-insensitive-safe path *comparisons* on Windows (never for display), ported from the reference extension's `discovery/pathUtils.ts`.
- `src/discovery/gitProject.ts` — no `vscode` dependency; `resolveProjectRoot(cwd)` shells out to `git rev-parse --git-common-dir` to find a cwd's project root, with an in-memory cache keyed by `normalizeFsPath(cwd)`. Shared as-is by both agents — Claude and Copilot sessions each record their own absolute `cwd`, so grouping into a project works identically regardless of which agent wrote it.
- `src/tree/sessionProvider.ts` — `SessionTreeProvider`, a `vscode.TreeDataProvider`. Node kinds: `AgentFolderNode` (`'claude' | 'copilot'`, only present when `detectAgentsInUse()` finds sessions for *both* agents somewhere on the machine — otherwise the tree collapses straight to project level, unchanged from before Copilot support), `ProjectGroupNode` (now carries an `agent`; one per non-`hidden` entry in `.vscode/session-deck.json` × whichever agent(s) actually have sessions under its resolved git root — backed by `~/.claude/projects` folders for `'claude'`, by `copilotSessionsForRoot()` for `'copilot'`; carries that entry's `maxSessionsShown`/`emoji`/`color`, already defaulted, shared across both agents' copies of the same project), `SessionNode` (also carries an `agent`; one per `.jsonl` file for Claude, one per `sessions` row for Copilot), and `ArchiveFolderNode` (a project's "Archived (N)" child, only present once it has ≥1 archived session). Reads session name/archived overrides from `DeckState` and the effective live status from `status/sessionStatus.ts` (Claude only); project names/membership/overrides come entirely from `config/workspaceConfig.ts`, with no agent field — `.vscode/session-deck.json` never declares which agent a project uses. `enforceArchiveCap` auto-archives a project's oldest active sessions past its own `maxSessionsShown` cap (see the bullet above), keyed per-agent (`` `${agent}:${normalizeFsPath(root)}` ``) so Claude and Copilot sessions for the same project are capped independently; its pure eviction decision lives in `tree/archivePolicy.ts`. `COLOR_SWATCH_EMOJI` maps a project entry's `color` to the emoji prefixed onto its label. `listAllSessions()` flattens every group's sessions across both agents unconditionally (archived included, never collapsed) for the search command and the Explorer view. `watch()` also watches the status directory, repainting the tree and (via a caller-supplied callback) the status decorations live.
- `src/tree/archivePolicy.ts` — no `vscode` dependency; `selectSessionsToArchive` is the pure "which sessions get auto-archived" decision `enforceArchiveCap` calls into — kept separate specifically so it's directly unit-testable (`test/suite/archivePolicy.test.ts`) without the rest of `sessionProvider.ts`'s filesystem/vscode plumbing.
- `src/tree/agentIcons.ts` — `agentIconPath(extensionUri, agent)`, the single place an agent's mark filename is chosen, shared by `sessionProvider.ts`, `activeSessionProvider.ts`, and `terminal/terminalService.ts` rather than each constructing the `Uri` inline. Returns a plain `Uri` for Claude, and VS Code's `{ light, dark }` icon form for Copilot (`copilot-mark.svg`/`copilot-mark-dark.svg`) — its near-black brand mark needs a white-filled variant to stay visible on a dark theme, unlike Claude's brand orange which reads fine on either.
- `src/content/sessionContentProvider.ts` — `SessionContentProvider`, a `vscode.TextDocumentContentProvider` registered on the `session-deck:` scheme. Parses a Claude session's `.jsonl` transcript into markdown on demand (`renderClaudeTranscript`), via the same `extractText`/`extractAssistantDisplayText` helpers, at `session-deck:/claude/<dirEncoded>/<id>.md`; `renderCopilotTranscript` does the Copilot equivalent from `listCopilotTurns()` (`## You`/`## Copilot` headings) at `session-deck:/copilot/<id>.md`.
- `src/config/state.ts` — `DeckState`, a thin wrapper around `vscode.Memento` (`context.globalState`) persisting session name overrides and archived-session ids — project names/membership live in `config/workspaceConfig.ts` instead.
- `src/config/workspaceConfig.ts` — reads/writes `.vscode/session-deck.json` in the first workspace folder: the sole source of truth for which projects show, what they're called, and their per-project overrides (`dangerouslySkipPermissions`, `maxSessionsShown`, `emoji`, `color`, `hidden` — see `WorkspaceProjectEntry`). Root comparisons go through `normalizeFsPath` too. `setWorkspaceProjectName`/`setWorkspaceProjectHidden` both go through the same small `updateWorkspaceProjectEntry` patch helper.
- `src/terminal/terminalService.ts` — `AgentTerminalService` (renamed from `ClaudeTerminalService`), resumes a session via `claude --resume '<sessionId>'` or `copilot --resume=<sessionId>` in a real terminal, chosen by `session.agent`: checks the right binary (`claude`/`copilot`) is on PATH per-command (`hasBinaryOnPath`/`probeBinaryOnPath`, each cached independently in a `Map<string, Promise<boolean>>` keyed by command name — replacing a single Claude-only cache — with a login-shell fallback for a narrower extension-host PATH, cleared on manual refresh via `clearBinaryCaches()`), uses shell integration with a `sendText` fallback. Tracks one `vscode.Terminal` (plus a display label, for `WaitingNotifier`) per session id (`sessionTerminals`/`sessionLabels`); `openSession` (the default) reuses/`.show()`s it if still alive, otherwise launches a new one; `openSessionInNewTerminal` always launches a new one regardless. `startNewSession` is the sibling for brand-new sessions — Claude-only for now (see the gap list above): plain `claude` (no `--resume`) at a given cwd, always a fresh terminal — `correlateNewSession` then watches `~/.claude/projects` to learn its real session id once Claude Code writes it, and registers it into `sessionTerminals` so it's no longer "untracked" once that resolves. `agentIconPath` (`tree/agentIcons.ts`, shared with `sessionProvider.ts` and `activeSessionProvider.ts`) picks the right mark, including Copilot's light/dark variant. `onDidEndTerminalShellExecution` (keyed by the `TerminalShellExecution` `launch()` started, via `sessionIdByExecution`) is where a resumed session's exit code is inspected for the "error" status — a backstop for both agents, though Copilot's own `session.error` event usually resolves first (see the status-dots bullets above). `trackTerminal`/`untrackTerminal` also start/stop a Copilot session's `copilotStatusWatcher` tail alongside its terminal (tracked per session id in `sessionAgents`, since only `trackTerminal`'s caller knows the agent).
- `src/terminal/sessionId.ts` — no `vscode` dependency; `assertSafeSessionId()`, the shared UUID-shape validation both agents' command builders need, extracted out of `claudeCommand.ts` once Copilot needed the same check.
- `src/terminal/claudeCommand.ts` — no `vscode` dependency; `buildClaudeResumeCommand`/`buildClaudeNewSessionCommand` turn a session id and the `--dangerously-skip-permissions` flag into the actual command string sent to a terminal. Split out of `terminalService.ts` specifically so this part — the part that decides what gets typed into a shell — can be unit-tested directly (`test/suite/claudeCommand.test.ts`). A session id is validated against a plain UUID-shaped pattern before being used bare (no shell-quoting): that's enough to stay a single, unambiguous argument in bash, PowerShell, and cmd.exe alike, which sidesteps ever having to pick a shell-specific quoting style.
- `src/terminal/copilotCommand.ts` — no `vscode` dependency; `buildCopilotResumeCommand` is Copilot's sibling to `claudeCommand.ts` — `copilot --resume=<sessionId>`, with `--allow-all` in place of `--dangerously-skip-permissions` when skip-permissions is requested. Same session-id validation, same reason for existing as a standalone, unit-tested module (`test/suite/copilotCommand.test.ts`).
- `src/status/reportStatus.ts` — no `vscode` dependency (deliberately no dependency on anything else in this project either); compiled to `out/status/reportStatus.js` and run as a standalone `node` process by Claude Code's own hook mechanism, entirely outside the extension host. Maps `UserPromptSubmit`→running/`Stop`→done/actionable-`Notification`→waiting hook payloads (read from stdin) to a coarse status file, and `SessionEnd` to deleting it, under `~/.claude/session-deck-status/<sessionId>.json`.
- `src/status/sessionStatus.ts` — no `vscode` dependency; a single, agent-agnostic status file per session id under `~/.claude/session-deck-status/<sessionId>.json` (still physically under `~/.claude/` for historical reasons, predating Copilot support — see its doc comment). `readSessionStatus` reads what wrote there — `status/reportStatus.ts` for Claude, `status/copilotStatusWatcher.ts` for Copilot, or `writeSessionStatus`/`markSessionError` called directly for the exit-code-inferred error backstop. `acknowledgeSessionStatus`/`readEffectiveSessionStatus` layer the "done or error, but already seen → blank" logic on top, in an in-memory `Map<sessionId, acknowledgedUpdatedAt>`. `clearSessionStatus` deletes a status file directly — used by `terminal/terminalService.ts`'s terminal-close listener as a safeguard against a status getting stuck when the underlying process dies without a `SessionEnd` hook or `session.shutdown` event getting a chance to fire.
- `src/status/copilotStatusWatcher.ts` — `CopilotStatusWatcher`, Copilot's live-status equivalent to `reportStatus.ts`, but structurally different: it runs in-process (started/stopped by `terminal/terminalService.ts` alongside a Copilot session's terminal, not spawned per hook event) and reads Copilot CLI's own internal `~/.copilot/session-state/<sessionId>/events.jsonl` activity log — written unconditionally by Copilot CLI for its own IDE/resume support — instead of its public, opt-in `hooks` config, so no settings mutation or subprocess-per-event is needed. Tails only bytes appended after `start()` (never backfills history), via a raw `fs.watch` + offset-tracked `fs.readSync`, splitting the growing NDJSON stream on newlines and carrying a trailing partial line into the next read. `classifyCopilotEvent` (pure, unit-tested — `test/suite/copilotStatusWatcher.test.ts`) maps its event `type` strings — pulled from the CLI's own bundled `session-events.schema.json` — to the same `SessionStatus` shape: `assistant.turn_start`→running, `permission.requested`/`elicitation.requested`/`user_input.requested`→waiting, their `.completed` counterparts back to running, `assistant.turn_end`→done, `session.error`→error, `session.shutdown`→clear. Writes through `sessionStatus.ts`'s `writeSessionStatus`/`clearSessionStatus`, so every downstream consumer works unchanged with no Copilot-specific branching.
- `src/status/sessionStatusDecorationProvider.ts` — `SessionStatusDecorationProvider`, a `vscode.FileDecorationProvider` keyed by a synthetic `session-deck-status:/<sessionId>` URI (set as each session `TreeItem`'s `resourceUri`). Colors the status dot on a decoration layer rather than `TreeItem.iconPath`, so it survives row selection; "error" gets its own `✗` badge rather than reusing the plain dot, so it's not just a second shade of red next to "running".
- `src/status/waitingNotifier.ts` — `WaitingNotifier`, wraps `node-notifier` to fire a real desktop notification on a watched session's transition into "waiting"/"error" — see the status-dots bullet above for the full reasoning (baseline-on-first-sight, transition-only, the `onActivated` click-through caveat).
- `src/tree/activeSessionProvider.ts` — `ActiveSessionProvider`, a second, independent `vscode.TreeDataProvider` (flat list, no project grouping — deliberately unchanged shape from before Copilot support, per-row `iconPath` is what tells the two agents apart here) registered into the built-in Explorer view container, filtering `SessionTreeProvider.listAllSessions()` down to whichever ones `AgentTerminalService.openSessionIds()` currently reports as open in this window. `STATUS_LABELS` maps each `SessionStatus` to its description-line text.
- `src/status/claudeSettings.ts` — no `vscode` dependency; `enableStatusTracking`/`disableStatusTracking`/`isStatusTrackingEnabled`/`isStatusTrackingPresent` additively, idempotently, and self-healingly merge/unmerge the 4 hook entries (one with a `Notification` matcher) into/out of `~/.claude/settings.json`, never touching any other hook or setting already there. "Ours" is recognized structurally (`OUR_HOOK_COMMAND`, matching `reportStatus.js` in the command string) rather than by exact-string match against the current command, so a stale path from an older install/layout still gets replaced or removed instead of silently left behind.
- `src/extension.ts` — wires the tree view, the content provider, and all commands: `sessionDeck.openSession` (resume in the shared terminal — the primary click), `sessionDeck.openSessionInNewTerminal` (always a fresh terminal), `sessionDeck.openSessionDangerously` (shared terminal, `--dangerously-skip-permissions`/`--allow-all` depending on `session.agent`), `sessionDeck.newSession`/`sessionDeck.newSessionDangerously` (plain `claude` at a project's root, no `--resume` — Claude-only, shows an explanatory message instead on a Copilot project node), `sessionDeck.viewTranscript` (the single-tab-reuse read-only view, agent-aware URI), `sessionDeck.search` (both agents' content), `sessionDeck.addProject`, `sessionDeck.editProjectList`, `sessionDeck.renameProject`, `sessionDeck.removeProject`, `sessionDeck.hideProject` (context menu only), `sessionDeck.renameSession`, `sessionDeck.archiveSession`/`sessionDeck.unarchiveSession`, `sessionDeck.copyLastResponse`/`sessionDeck.copySessionInfo` (context menu only, no inline icon — the row already has four; both branch on `session.agent` to read from the right storage backend), `sessionDeck.enableStatusTracking`/`sessionDeck.disableStatusTracking` (Command Palette only, Claude-only).

Several of the above are adapted from **[Claude Sessions Explorer](https://github.com/ShahadIshraq/claude-session-vs-code-extension)** (cloned and read directly rather than guessed at): its `discovery/content.ts` (display-text extraction + prompt filtering), `discovery/pathUtils.ts` (case-insensitive path comparison), `discovery/service.ts` (mtime-keyed caching), and `terminal.ts` (shell-integration-aware `claude --resume`, ported near-verbatim into `terminal/terminalService.ts`, plus the one-terminal-per-session tracking it already used). Its webview-based UI and destructive session deletion were *not* adopted.

`discovery/claudeStorage.ts`, `discovery/pathUtils.ts`, `terminal/claudeCommand.ts`, `terminal/copilotCommand.ts`, and `status/copilotStatusWatcher.ts`'s pure `classifyCopilotEvent`/`splitLines` have no `vscode` import, so they're the only files with real unit tests (`src/test/suite/*.test.ts`, run via Node's built-in test runner — `npm test`, no Extension Development Host needed). Everything else touches the `vscode` API directly and isn't covered by anything beyond manual testing (via `F5`) today.

## Running it

1. `npm install`
2. Press `F5` (or Run → Start Debugging) — the default build task (`compile`, a one-shot `tsc -p ./`) runs first and *blocks* until it fully succeeds, then launches an Extension Development Host window, opened directly on `X:\demo-projects` for testing (see `.vscode/launch.json`).
3. Open the "Session Deck" icon in the activity bar.

The pre-launch task is intentionally the blocking `compile`, not the background `watch` — using `watch` here raced against F5 (the host could launch mid-rebuild, right after an edit, and load a half-written `out/extension.js`, crashing that window outright). If you want live-reload while iterating instead of re-pressing F5 each time, run `npm run watch` yourself in a separate terminal; `Ctrl+Shift+F5` (Restart Debugging) after a change is the simplest way to pick up edits either way.

`npm test` compiles then runs the vscode-free unit tests above; `npm run lint` runs ESLint (`eslint.config.mjs`, flat config, `typescript-eslint`'s non-type-checked `recommended` preset) over `src`.
